# 全项目详细中文注释设计

## 1. 目标

为项目自有的生产源码和测试源码补充准确、可维护的中文注释，使维护者无需反复追踪实现细节即可理解模块职责、公开接口、复杂流程和关键约束。

同时建立持续约束，要求后续新增或修改的代码同步维护详细中文注释，避免本次治理成为一次性工作。

## 2. 范围

纳入范围：

- Rust 生产源码、测试源码和项目自写构建脚本；
- TypeScript、Vue、CSS 生产源码及测试源码；
- 项目自有 Protobuf 定义；
- 与源码注释要求直接相关的项目规则、评审清单和 lint 配置。

排除范围：

- `target/`、`node_modules/`、`dist/` 等构建产物或依赖目录；
- `Cargo.lock`、`package-lock.json` 等锁文件；
- `prost` 等工具生成的源码；
- `im-app/ui/public/vendor/gt4.js` 等第三方代码；
- 纯数据文件、图片等不承载程序逻辑的资源。

## 3. 注释原则

采用“语义级详细注释”，不追求逐行解释。

必须说明：

1. crate、模块和重要文件的职责、边界及主要依赖；
2. 公开类型、函数、方法和常量的用途；
3. 公开 API 的参数、返回值、错误条件、副作用和调用约束；
4. 非自明字段、状态值和协议字段的业务含义、单位及取值限制；
5. 复杂私有逻辑的状态转换、并发关系、生命周期、重试策略和失败处理；
6. 加密、签名、压缩、帧格式及兼容性逻辑背后的协议约束；
7. 测试覆盖的场景、关键准备步骤及核心断言意图；
8. 临时兼容、规避措施或反直觉实现存在的原因。

不应添加：

- 对变量赋值、简单条件判断等自明代码的机械复述；
- 无法从代码、协议或已有设计中验证的推测；
- 很快会与实现脱节的逐行流程翻译；
- 仅重复函数名或类型名、没有补充语义的信息。

## 4. 语言与格式

- 新增和改写的说明性注释统一使用简体中文；
- 协议名、字段名、算法名、HTTP 头和报文格式保留原始英文标识；
- 有价值的既有英文注释翻译为中文，不丢失协议细节和设计依据；
- Rust 公开 API 使用 Rustdoc `///`，crate 或模块说明使用 `//!`；
- TypeScript 和 Vue 的导出接口、组合式函数及复杂服务函数使用 JSDoc；
- 行内 `//` 注释只用于解释局部决策、阶段或不变量；
- CSS 和 Vue 模板仅按区域或非自明交互分段说明，不逐条解释样式声明或标签。

## 5. 分阶段执行

按以下顺序分批处理，每批同时覆盖对应测试：

1. `im-common`、`im-proto` 和 `proto`：公共类型、加密、帧头和协议定义；
2. `im-chat`：连接、帧处理、心跳、重连和相关测试；
3. `im-http`：加密 HTTP、业务客户端和协议兼容逻辑；
4. `im-store`：数据模型、Schema、查询行为和存储测试；
5. `im-app` Rust 后端：状态管理、认证、聊天和群组命令；
6. `im-app/ui`：组合式函数、服务、类型、组件交互、样式分区及测试；
7. 全仓复查：遗漏 API、遗留英文说明、术语一致性和无价值注释。

每批保持“仅注释或注释约束变更”，不夹带业务重构和行为修改。若检查发现实现缺陷，单独记录，不在本任务中顺带修复。

## 6. 持久约束

新增项目级 Cursor 规则：

`/Volumes/TRANSCEND/works/objects/rust/broadcast/.cursor/rules/chinese-comments.mdc`

规则始终应用于本项目，并要求：

- 新增或修改模块、公开 API 和复杂逻辑时同步维护中文注释；
- 注释说明意图、约束和失败行为，不复述语法；
- 修改实现后同步检查相邻注释是否仍然准确；
- 评审时拒绝缺少必要中文注释或注释与实现不一致的变更。

新增项目贡献说明或评审清单，记录相同的验收标准，供非 Cursor 工作流使用。

Rust 文档 lint 采用渐进策略：某个 crate 完成注释基线并通过检查后，再为该 crate 启用 `missing_docs` 警告。初期不直接使用 `deny`，避免历史缺口阻塞全部开发。

前端当前没有成熟的注释 lint 基线，因此先通过项目规则、评审清单和人工复查约束；不为本任务额外引入重量级 lint 依赖。

## 7. 验证策略

每批完成后执行：

- `cargo fmt --all --check`；
- 对应 crate 的测试；
- 对应 crate 的 Clippy 检查；
- 涉及前端时执行类型检查、单元测试和生产构建；
- 搜索剩余英文注释并逐条判断是否应翻译；
- 抽查注释与实现、协议定义和测试行为是否一致。

全批次完成后执行 workspace 级 Rust 测试和前端完整验证。

注释变更原则上不应改变运行行为。任何测试结果变化都视为异常，必须先定位原因，不得通过修改断言掩盖。

## 8. 验收标准

完成条件：

1. 纳入范围的每个主要模块均有中文职责说明；
2. 所有项目自有公开 Rust API 均有准确的中文 Rustdoc；
3. 导出的 TypeScript/Vue 接口及复杂组合式函数均有中文 JSDoc；
4. 协议、加密、连接、重试、状态机和持久化等复杂逻辑均说明关键约束；
5. 测试均能表达场景意图，复杂准备过程和关键断言有必要说明；
6. 有价值的既有英文注释已翻译，协议原始标识得到保留；
7. 不存在大面积机械逐行注释或未经验证的推测性说明；
8. 项目规则和评审清单已落地，Rust 文档 lint 按 crate 渐进启用；
9. 所有相关格式化、测试、静态检查和构建验证通过。

## 9. 风险控制

- 大文件分批处理并单独复核，避免一次性巨型 diff；
- 协议注释必须与 `broadcast.proto`、现有报文实现和测试相互核对；
- 对无法确认的业务含义不编造说明，记录为待确认项后向维护者求证；
- 注释治理期间不重构业务，降低行为回归风险；
- 每批验证通过后再进入下一批，便于定位问题和审查变更。
